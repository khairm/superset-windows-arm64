# Fork feature manifest

This file is the source of truth for **what our fork adds on top of upstream
superset**. The nightly upstream-merge workflow greps every marker below against
the merged tree; **if any marker is missing the merge is rejected** (a feature
was dropped or an upstream change clobbered it) and the build hard-aborts into
the recovery loop. Markers are deliberately distinctive identifiers that only
exist because of our feature code.

When you add a new custom feature, add a marker row here in the same commit.
When upstream **deprecates/removes** a feature we mirrored, remove its marker row
in the merge that drops it (the only legitimate way a marker leaves this list).

| Companion alerts name their chat | every phone/watch alert — ready (`g`), agent-error (`e`) and blocked-question — says WHICH chat it is about: title `<project> · <workspace>`, body `<tab> — <event text>`, with the tab named only when the workspace has 2+ tabs and a title resolved. The three names ride the FCM push as PLAINTEXT under an explicit owner waiver recorded 2026-08-16 ("i dont care if google sees it", re-confirmed via AskUser) — and ONLY those three: question text, option text, file paths, branch names and every other free string stay banned, the exempt key set `{pn,wn,tn}` is enumerated by a test, and v1/v2 keep their 160-byte leak tripwire while only v3 gets 2048. Wire schema v3 is closed PER (VERSION, KIND) — `q`=[v,k,i,w,n,x,t,pn,wn,tn,tc], `g`=[v,k,i,w,x,gx,t,pn,wn,tn,tc], `e`=[v,k,i,w,x,t,pn,wn,tn,tc], `c`=[v,k,i,w,x,gx,t] — with EVERY key always present and `""` spelling absence, because the phone's parser is exact-equality in both directions and a missing key would silence the alert rather than degrade it; the host mirrors the phone's golden vectors byte-for-byte in its own suite. `g` and `e` deliberately no longer share a key set: a ready alert must carry `gx` (13 digits, the OUTCOME event's instant — the same one the alert id hashes, never anything send-shaped, since presence gating can send an earlier finish later) and a non-empty `t` (the terminal handle, read off the ALERT ROW rather than the nullable context resolver, because it is the notification's identity on the phone and a failed context lookup may cost names but never identity), while an error alert carries neither and an `e` smuggling `gx` throws. Names are sanitised TOTALLY (never throws: controls/C1/U+2028/U+2029/newlines stripped, 256-byte UTF-8 budget, truncation walked by CODE POINT so an emoji can never be cut into a lone surrogate) and resolved INSIDE the send — fresh on every retry, never cached on a held alert — so a workspace renamed mid-hold buzzes with its new name, and a resolver that throws costs the names, never the notification. Tab titles live only in the renderer, so a per-workspace snapshot (`pane.kind==="terminal"` + `pane.data.terminalId`, title precedence tab rename > pane rename > live terminal title > nothing, one terminal in two differently-named tabs ⇒ no tab name) is pushed over two new PROTECTED tRPC mutations and held in a bounded process-local registry that re-derives every workspace↔terminal relationship from `host.db` before an atomic replace. Lifecycle alerts now RETRACT — deliberately overriding the old "lifecycle alerts are not retracted" invariant rather than layering over it: reading the chat on the desktop (focus-clear or sidebar mark-read, and ONLY when a green dot was actually removed — never the resync's cold-start seeding, which would mass-retract on every launch) or the SESSION ENDING sends a v3 `c`, and alert ids are hashed from the FINAL outcome event's instant so `markLifecycleSeen` can recompute one after a host restart with no schema change. `(ONE-BUZZ-UNTIL-READ)` bounds the noise that made retraction necessary in the first place: measured overnight on v0.1.0, one long-running chat finished sixteen times ~15 minutes apart while the user was away and stacked sixteen buzzing notifications for a single unread conversation. A delivered ready alert superseded by a NEW WORK CYCLE is therefore retired SILENTLY — the row is kept as the cycle's dedupe record, the notification is left standing, and the next `g` for that terminal replaces it in place (the phone keys ready notifications by terminal handle; `t` has been on the v3 wire since the feature shipped). One live card per unread chat, updated quietly however many turns it takes; reading it retracts and resets, so the next finish buzzes fresh. A silently retired alert is not gone — it is STANDING: its row survives in a distinct state, and the one `c` it is still owed fires later, exactly once, whether the user reads the chat or the session ends, carrying that alert's own `gx` so the phone cancels the finish it is actually holding rather than whatever card is showing (a supersession in flight UPGRADES: new-cycle then session-end resolves as a session end when the send lands). Because the green dot is cleared by the agent starting work again while the phone keeps the card, the desktop also keeps a per-terminal OUTSTANDING-READY record beside its seen marks: opening a chat that is already running again reports a read for the finish that record names, the record is retired only when a host actually consumes the report AND only up to the generation that host acknowledged (a newer finish landing mid-report keeps its own record), and the resync repairs the ones that were dropped — under the same cap, rotation and cooldowns as the existing repair, and never inventing one out of its own replay. Generations are ordered by a per-terminal MONOTONIC lifecycle instant (`max(now, previous+1)`, anchored on the persisted binding so it survives a restart) rather than the raw wall clock, because an NTP step-back would otherwise stamp a newer finish behind its predecessor — which the phone rejects as stale, the host cannot retract, and the renderer records as reported. And a read is bounded by its OWN instant: `markLifecycleSeen` retires every generation at or before `seenThroughAt` and leaves later ones alone, so a delayed or resync-replayed read of an earlier finish can never retract work the user has not seen. Its "nothing ever existed, so send nothing" branch is bounded the same way — per terminal, against the last lifecycle instant host.db recorded before the manager started (read once at bridge start), because a wall-clock start compared against a monotonic generation lets a restart inside a backstep "prove" that an alert the previous process actually sent never existed; unreadable or absent restart evidence disables the proof rather than trusting it, since a blind `c` the phone drops is the safe failure and a swallowed retraction is not. Every other retirement still fires its `c` — a session end (the chat is gone, so tapping it would open nothing) and a read (the event that resets the cycle) — and `e` alerts are excluded from the rule entirely, because an agent that died is not superseded by later work and an unseen error must not be quietly folded away. Retract sends (v1 `r` AND v3 `c`) now use the 24 h `RETRACT_TTL_MS` as the FCM envelope TTL, closing a latent gap where a handset off the network for 15 minutes kept a notification for an answered question | `(ALERT-CONTEXT-NAMES)` |

| Watcher ignores replayed and counterfeit turn-ends | the JSONL watcher emits ONE turn-end of its own — a user interrupt — because Claude Code fires no hook for it; every other turn-end, including a terminal API error, is the hook's (Claude Code runs its StopFailure hooks whenever the turn's last record is an api-error and superset-notify.py's StopFailure branch answers `Stop`), so hook-is-truth holds and the watcher's api-error contribution is auto-resume signalling only, which asserts no dot state. The watcher's own emit still bypasses superset-notify.py, and the renderer clears the background-running axis on every non-`BackgroundRunning` agent event, so a `Stop` fired off the wrong line wipes the blue the hook just restored (live: compact-end `BackgroundRunning`, then 763ms later the watcher re-parsed the compaction-rewritten transcript, matched a HISTORICAL "Request interrupted by user" and greened the dot under a still-running background shell). Two gates now stand between a matched line and an emit. FIRST, the line must BE an interrupt: the marker was a raw PHRASE match, and this repo's own agent traffic quotes it constantly — measured over 10,695 local transcripts the phrase predicate matched 1217 lines of which 70 were quotes (tool_results and long teammate messages), and 9 of the 10 interrupt-releases in a live log window were false `Stop`s fired MID-TURN. So it is parsed to Claude Code's EXACT synthetic record — a user entry whose message content is a single `text` block equal to `[Request interrupted by user]` — which drops every quote and keeps all 1147 genuine records. SECOND, the turn must have ended JUST NOW: Claude Code re-presents already-written entries (compaction rewrite, post-truncation re-read from offset 0, discover-poll whole-file read), so each entry is replay-gated on its own `uuid` (already judged → never counts again, at any age) and `timestamp` age, which must be no older than 120s and no further in the future than a 5s clock-skew tolerance (a backward NTP step would otherwise make ALL history read as fresh). A file that already existed when the watcher started is never replayed whole through a cold gate, but it is no longer tailed blind either: Codex seeds it to EOF, and Claude re-reads a bounded 256KB tail under a third gate layer — a pre-start fence suppressing every entry stamped strictly before the watcher started (no skew slack: both stamps come from the same machine's clock). The fence is held on the file's own state, not a per-pass local, so a read that throws after the offset was rewound cannot make the retry re-read that history UNFENCED. Seeding blind would SWALLOW an append that landed between `fs.watch` going live and the deferred seed reaching that file, and an interrupt has no hook fallback at all, so that dot would stay stuck; the tail is bounded because reading a multi-megabyte transcript synchronously at startup is what starves the renderer. A blocked match emits NOTHING, so the hook's blue stands and an AUTO compact no longer gets a false turn-end. A genuine interrupt still emits a bare `Stop` (the (BA) blue latch has no self-clear, and the Agent-Complete chime is Stop-only), and that verdict is explicit — never derived from best-effort marker cleanup | `(WATCHER-BLUE-STOMP)` |

Pid reuse is guarded by start times: the root's is captured at session open (the Windows analogue of the pgid/tty capture) and re-checked on every pass, so a root pid that has been recycled targets NOTHING; a candidate child must have started at or after its parent (a process that predates its "parent" is an orphan on a recycled pid); and a candidate whose start time is unreadable is never targeted — the kill fails safe and leaks a process, which the survivor report then names. There is deliberately NO synchronous Windows enumerator: a blocking PowerShell spawn freezes the daemon's only event loop and stalls every session's IO, so `readProcessTable()` warns ONCE and returns empty (UNKNOWN, never "no descendants") and the whole reap lives in the async escalation chain — which on Windows therefore also runs for a SIGKILL request (immediately, no grace delay), since POSIX's synchronous volley has no counterpart there. The survivor report is accurate instead of always claiming failure | `(WIN-PROCESS-TREE)` |
| Terminals survive an app install | the detached pty-daemon is what actually owns the user's shells, and it already survives a host-service restart by design — but it could never survive an APP INSTALL, because everything it executed lived in `$INSTDIR`: its process image was `Superset.exe` itself, it mapped `conpty.node` out of `resources\app.asar.unpacked`, and it inherited host-service's cwd (the spawn passed none). Any ONE of those is enough that Windows refuses to let the installer replace the file, so the installer's only remaining move is to kill the daemon — taking every live terminal with it. Before the FIRST daemon spawn on Windows the supervisor therefore materialises a self-contained runtime under `%LOCALAPPDATA%\Superset\pty-runtime\<key>\`: the Electron runtime files from the install root with the binary copied under a DIFFERENT NAME (`superset-ptyd.exe` — electron-builder's one-click NSIS kills running processes by matching `${APP_EXECUTABLE_FILENAME}`, so a renamed image is not a target), `locales\`, the daemon's own `dist/main/pty-daemon.js` plus the ENTIRE hash-named `chunks/` dir (never an enumerated chunk list — that is `SCREENREADER-GUARD-DRIFT` in another costume), and `node-pty` + `@lydell/node-pty-<platform>-<arch>` placed where ordinary Node resolution walking up from the script finds them. 364 MB, against 2.21 GB for the whole install dir, because `resources/` (the 1.2 GB asar the daemon never reads) is excluded structurally rather than by filter. The daemon is then spawned with that exe, that script and an explicit `cwd` inside the runtime, so it holds no handle anywhere in `$INSTDIR`; host-service itself stays in the install dir and still dies with the app, and the next boot re-adopts the surviving daemon over its org-hashed named pipe exactly as it already does across host-service restarts. The cache key is `<pty-daemon package version>-e<electron version>-<sha256(entry script)[:12]>`: the package version is the SAME value `EXPECTED_DAEMON_VERSION` already uses to judge a running daemon stale, so no new notion of "a different daemon" is introduced; the Electron version is in because the copied binary IS the runtime; and hashing the 42 KB ENTRY transitively covers the chunk set, since chunks are content-hash-named and referenced by name from it. An app release that does not touch the daemon reuses the existing runtime for one read plus one stat; a cold materialisation costs ~8 s and runs on the ASYNC fs API inside host-service — never on Electron's main thread, whose blocking startup fs starves the `superset-app://` loader and blanks the window for minutes. Crash-consistent by construction, because the installer can hard-kill at any moment: everything stages in `<key>.tmp-<rand>`, the copied binary is SMOKE-TESTED for real (`superset-ptyd.exe -e "require('node-pty');require('node-pty/requireBinary').requireBinary('conpty.node')"` must exit 42, which proves the file set boots AND that the native addon actually LOADS under this Electron's ABI). That second require is load-bearing, not decoration: @lydell's `WindowsPtyAgent` loads `conpty.node` LAZILY, in its constructor, so `require("node-pty")` on its own imports nothing but JS and a runtime whose prebuild is missing, quarantined or built for the wrong arch passes the test, commits `.ready`, and then fails at the first terminal the user opens. Measured on the shipped Electron against a copy of the packaged `node_modules` with `conpty.node` deleted: the JS-only script still exits 42, the addon-loading one exits 1. The load goes through node-pty's OWN platform/arch resolver, so nothing here hardcodes win32-arm64, no DLL list has to be asserted, and an Electron upgrade that adds a file cannot silently produce a dead runtime, the `.ready` marker is written INSIDE the staging dir, and the rename into place is the single atomic commit. A directory without `.ready` is not-ready and is rebuilt — and so is one WITH `.ready` whose `superset-ptyd.exe` or entry script has gone missing, because the marker is an ordinary file in an ordinary user-writable directory and the binary beside it is unsigned, freshly written and freshly RENAMED, which is an antivirus heuristic bullseye. Trusting the marker alone would make every spawn ENOENT while still reporting `reused`, opening the crash circuit and leaving the user with NO terminals at all — the one outcome this feature exists to prevent — because the loud fallback below only ever fired on a MATERIALISATION failure. Two stats on reuse close that. Reclaiming an old runtime is the one operation here that can destroy a working install, so it is gated twice: a `.refs/<pid>.json` record claims a key for a live daemon pid (a recycled pid can only ever over-protect), a runtime committed in the last five minutes is skipped outright because the daemon it was built for may not have a pid to claim it with yet, and every removal RENAMES the directory first, which Windows refuses while it is a live process's cwd or holds a mapped image — so a lost ref file degrades to "skipped, retried next spawn", never to a half-deleted live runtime whose plain-`.js` conout worker and console-list agent would be unlinked out from under it. A materialisation failure falls back to today's install-directory spawn but says so LOUDLY (`pty_daemon_runtime_sidecar_unavailable` plus a console error naming the consequence), and so does a relocated runtime that materialises fine but cannot actually start a daemon: it is discarded (`pty_daemon_runtime_sidecar_spawn_failed`) and the spawn is retried from the install directory in the same breath. Discarding removes the ready marker and NEVER the files — another org's daemon may be live in there, and unlinking its plain-`.js` conout worker underneath it is exactly what the rename gate exists to prevent: believing you are protected when you are not is worse than not being protected, and leaving the user with no terminals at all is worse than both. `fs.access` is deliberately NOT used to probe the sources — measured on the shipped Electron 41.10.3, `access` answers ENOENT for every DIRECTORY inside `app.asar` while `stat` and `readdir` work, so an `access`-based probe passes every real-filesystem test and then fails on every packaged install | `(PTY-RUNTIME-SIDECAR)` |

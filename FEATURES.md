# Fork feature manifest

This file is the source of truth for **what our fork adds on top of upstream
superset**. The nightly upstream-merge workflow greps every marker below against
the merged tree; **if any marker is missing the merge is rejected** (a feature
was dropped or an upstream change clobbered it) and the build hard-aborts into
the recovery loop. Markers are deliberately distinctive identifiers that only
exist because of our feature code.

When you add a new custom feature, add a marker row here in the same commit.
When upstream **deprecates/removes** a feature we mirrored, remove its marker row
in the merge that drops it (the only legitimate way a marker leaves this list).

| A held push survives a restart for real | the durable fence rebuilt `armed` correctly and the reconstruction was still INERT: `QuestionStore` is memory-only and comes back EMPTY, so the fire-time re-check asked it about every rebuilt row, was told the question does not exist, and discarded it on the FIRST away sweep — before it could ever buzz. Every push held across a host-service restart was lost, which is exactly what the durable fence was added to prevent, and the test that covered it passed because its fixture handed the probes a question the production store would not have. The fence row now carries what FIRING needs — terminal and workspace ids, and the `transcript_path`/`tool_use_id` pair — none of which reaches FCM. A rebuilt row is marked store-orphaned and is NOT discarded: it is asked once, against its own transcript and with guard 1's own machinery, whether it was answered while the host-service was down. Only a positive `resolved` cancels it; unreadable, missing, throwing, or a check that outruns its deadline all mean CANNOT CHECK, and it fires on the ordinary away rules — a stale buzz self-corrects the moment the user taps it, a lost buzz never does. The sweep HOLDS an entry whose check is still in flight so a question about to be proved resolved cannot buzz first, and a re-capture ADOPTS the row back to the ordinary re-check | `(PUSH-ARMED-ORPHAN)` |
| Only a person's keystrokes count as presence | the keystroke half of presence stamped on the FRAME TYPE — every `{type:"input"}` the renderer's terminal socket delivered — and xterm fires `onData` for two unrelated things: a person typing, and the terminal ANSWERING A QUERY the program on the other end sent (Device Attributes, cursor position, XTGETTCAP). xterm tracks the difference internally as `wasUserInput` and does not expose it on `onData`, so a TUI polling the cursor position registered as a user sitting at the desk several times a second with nobody in the room, and every companion push stayed held for as long as that program ran — indefinitely, and invisibly. The renderer now witnesses what only it can see: real keydown/paste/composition events, captured on the xterm CONTAINER rather than the textarea, because xterm dispatches `onData` synchronously inside its own textarea handlers and a listener beside them would miss the first keystroke of every burst. A frame is tagged `human: true` only when such an event happened within the tagging window, and the host-service stamps presence only for frames carrying it. Absence is never read as human — an older renderer omits the field and simply stops driving presence by keystroke, which leaves the 15 s desktop beacon and errs toward AWAY, i.e. toward buzzing | `(HUMAN-INPUT-TAGGED)` |
| A curation change moves the tree's sequence | `/v1/tree` is filtered through the sidebar mirror, so curation decides what the phone renders — and the mirror was written entirely outside the bridge by the renderer's `sidebarMirror.sync` mutation, so nothing minted an event and `gseq` never moved for it. The heartbeat compares `gseq` alone, so it kept answering `treeStale: false` while pins, membership and placement changed underneath, and the phone went on stamping 'updated just now' over a list that no longer matched the sidebar — indefinitely, because the change that mattered had already happened and no later event could repair it. A sync now hashes its own snapshot (key-sorted, so the renderer's unstable live-query row order is not a change, and `appLaunchId`-inclusive, because the same rows under a new launch release every until-next-launch snooze) and compares it with the hash the previous write stored. Only a write that CHANGED the mirror publishes, through the same `events.publish` question events use, so the next heartbeat reports `treeStale` and the client refetches. The renderer's five-minute heartbeat re-push of an identical snapshot publishes NOTHING — announcing those would invalidate every client's tree cache twelve times an hour. The frame carries no curation, only counts: the mirror is a whole-snapshot replace and a delta on the wire would be a second, independently wrong description of it | `(MIRROR-CHANGE-GSEQ)` |
| A cancelled push still records what it sent | the mirror writer's push loop reported a sync only when its send resolved AND its loop had not been cancelled, and it reported no value — the hook recorded whatever signature its own effect had closed over. So a push that resolved after a newer signature cancelled its loop changed `host.db` and recorded nothing, leaving the hook believing an older snapshot was installed. If curation then reverted to exactly that signature — undo a bin, unsnooze, restore a thread — the effect's skip-gate matched, no push was issued, and the intermediate curation stayed installed, hiding a restored thread from the phone until the five-minute heartbeat. The loop now reports the snapshot it ACTUALLY SENT on every resolved send, cancelled or not (a FAILED send still reports nothing — nothing landed), and the hook records that snapshot's own signature, so the skip-gate re-arms against what the database holds rather than against whichever loop survived. Ordering is safe because the shared in-flight promise serialises sends. Covered by the renderer test file this hook had never had | `(MIRROR-SYNC-CANCEL-RACE)` |
| A reconnected event bus resyncs the dots | the renderer's agent dots are driven entirely by host-service WS events, and that bus is fire-and-forget on both ends: `EventBus.broadcast` writes to whichever sockets are connected and keeps no queue, and the client replays only its `fs:watch` commands on open. Every agent-lifecycle event emitted while a renderer was disconnected was therefore DESTROYED — and the working/permission states cannot self-heal from that, because an agent blocked on a question emits no further hook events. A host-service restart left one window's bus dead for 7h43m with a pending AskUserQuestion whose red dot never rendered and never could. The host now serves a durable snapshot of every live terminal binding, with `pendingPermission` derived from the `.askq` marker rather than `lastEventType` (the notify hook rewrites red-clearing events to `SubagentActive` while a question is pending, so the binding's last event commonly reads yellow for a terminal that is actually blocked on the user). The renderer refetches it on every socket open — and again if the workspace rows hydrate afterwards — replays each row through the ordinary status path MINUS the chime and native-notification path, and clears the working/permission latches and background-running blue of terminals the host POSITIVELY DISOWNS — it has a `terminal_sessions` row for them but no live binding. A terminal the host has never minted (a re-issued pane terminalId whose hook POSTs all return `ignored: true`, whose dot is painted locally by the Electron fallback) is absent from the live bindings for a reason that has nothing to do with its agent, so it is skipped and logged rather than cleared. Review (green) is left to the seen-mark path, which owns it. A failed snapshot fetch reconciles NOTHING and logs loudly rather than clearing dots on unknown truth. Two supports ship with it: a disconnected socket re-reads the local PSK from the coordinator, so a host that restarted with a new secret cannot strand the socket until some unrelated render refreshes it; and a sidebar pill says the bus is down once it has stayed down past a 15s grace, because a frozen dot and an idle agent look identical | `(BUS-RESYNC)` |
| A dispose that fails says so | a dispose whose daemon close never confirmed left the row `active` with only `disposeRequestedAt` stamped and broadcast NOTHING: the renderer was never told, its socket was already closed, its re-dial was refused, and the transport latched `_terminated` — a red "Disconnected" pane that could not self-heal until the reaper's next pass (observed at 21 minutes). Four honesty fixes cover that window: the failed close now broadcasts the same `terminal:lifecycle` exit the confirmed path does and logs loudly (as does every refused attach, which used to travel only down the socket and leave zero host-side trace); `terminal.killSession` returns the real outcome (`dispose-pending` + reason) so no caller — renderer toast, CLI, MCP/SDK agent — can claim a kill it did not get; attach REFUSES to respawn a row carrying the intent-to-kill stamp, and only an explicit create clears that stamp, so a respawned terminal is no longer reaped seconds later by its predecessor's; and create is atomic across `makeDaemonPty` + the row insert, so a throw there (SQLITE_BUSY is live) can no longer leave a live PTY with no row for the reaper to kill under a user who thought they had a terminal. The notification ingest splits its one silent drop into three outcomes (broadcast / `null-origin-workspace` / `unknown-terminal`, the last an invariant violation logged as `console.error`), all still answering HTTP 200 because a non-2xx makes the bash hook fall through to the legacy Electron path; both hook writers log the response BODY, since every outcome is a 200 and the status code alone cannot tell a delivered dot from a dropped one | `(DISPOSE-LIMBO)` |
